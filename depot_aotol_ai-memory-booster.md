#     ai-memory-booster how to install

## **1\. Vue d'ensemble du projet**

**AI Memory Booster** (développé par *Aotol Pty Ltd*) est un module open-source léger et embarquable conçu pour doter n'importe quel LLM d'une **mémoire persistante à long terme**, fonctionnant entièrement en local (on-premise / hors ligne).

* **Stack technique :** 97,5 % JavaScript, 2,1 % Shell, 0,4 % CSS.  
* **Dépendances d'infrastructure :**  
  * **Ollama** pour l'exécution locale des modèles de langage (par défaut llama3.2) et la génération d'embeddings.  
  * **ChromaDB** comme base de données vectorielle pour stocker et rechercher les souvenirs par similarité.  
* **Modes de déploiement :** utilisable comme package NPM (npm install ai-memory-booster), en tant que service API REST autonome (npx ai-memory-booster start), ou piloté via une interface web dédiée (web/ai-memory-ui).

## **2\. Structure du dépôt**

Le projet totalise 43 commits (branche unique main, aucune release publiée) et s'organise autour de 4 répertoires principaux :

## **3\. API et fonctionnalités exposées**

Le module propose une interface programmatique simple centrée sur le cycle de vie de la mémoire et l'inférence augmentée :

* storeMemory(summary, userMessage, aiMessage) : injecte manuellement une entrée mémoire (résumé \+ échange brut).  
* retrieveMemory(query) : recherche les souvenirs les plus pertinents et renvoie un objet contenant id, distance (plus elle est faible, meilleure est la correspondance), summary, userMessage, aiMessage et timestamp.  
* forget(id) **/** forgetAll() : suppression ciblée par UUID ou purge complète de la mémoire.  
* chat(message) : conversation contextuelle s'appuyant sur la mémoire stockée (avec apprentissage continu si learnFromChat est activé).  
* generate(prompt) : génération de texte ponctuelle enrichie par la mémoire.  
* getLlmSpec() : retourne les spécifications du modèle LLM actif.  
* configManager : accesseurs dynamiques (getPort(), setPort(), etc.) permettant de modifier la configuration à chaud.

## **4\. Paramètres clés de configuration (**config.json**)**

La configuration (éditable via JSON ou via l'interface web) révèle plusieurs mécanismes internes intéressants :

* **Gestion du cycle de vie LLM :** baseKeepAlive (3000 ms) et extendedKeepAlive (10000 ms) contrôlent combien de temps le modèle reste chargé en mémoire vive après un appel.  
* **Recherche vectorielle :** vecteurs de dimension 768, récupération par défaut des 3 résultats les plus proches (similarityResultCount) avec un seuil de similarité fixé à 0.7 (similarityThreshold).  
* **Consolidation et limites :** troncature/contrôle des messages longs (maxUserMessageCharacterLimit: 10000), résumé automatique plafonné à 256 caractères (summaryCharacterLimit, consolidateConversationThreshold) et seuil de confiance de classification (categorySureThreshold: 49).  
* **Modes avancés :** apprentissage automatique depuis le chat (learnFromChat: true), mode archivage (archive: false), et personnalisation du rolePrompt pour éviter les confusions de pronoms entre l'utilisateur et l'IA.

log "Démarrer l'UI  : cd web/ai-memory-ui && npm run dev"

### **Détail des flags clés**

| Flag CMake | Rôle sur le CIX CD8180 |

## **Utilisation et déploiement**

### **1\. Construction sur l'hôte Ubuntu 26.04 `x86_64`**

| chmod \+x build-llama-cpp-cd8180-deb.sh ./build-llama-cpp-cd8180-deb.sh  |
| :---- |

*(Optionnel : vous pouvez figer un tag précis avec `LLAMA_REF=b5200 ./build-llama-cpp-cd8180-deb.sh` ou désactiver libcurl avec `ENABLE_CURL=OFF`.)*

### **2\. Installation et démarrage sur l'Orange Pi 6 Plus (`aarch64`)**

| scp llama-cpp-cd8180\_\*\_arm64.deb user@orangepi6plus:/tmp/ ssh user@orangepi6plus "sudo apt-get update && sudo apt-get install \-y /tmp/llama-cpp-cd8180\_\*\_arm64.deb"  |
| :---- |

Ensuite, sur la carte : 

| \# 1\. Déposer un modèle GGUF (ex. Q4\_0 optimal pour KleidiAI/i8mm) sudo cp mon-modele-Q4\_0.gguf /var/lib/llama-cpp/models/model.gguf sudo chown llamacpp:llamacpp /var/lib/llama-cpp/models/model.gguf \# 2\. Démarrer et vérifier (vérifiez dans les logs la détection Vulkan Immortalis-G720) sudo systemctl start llama-server.service sudo journalctl \-u llama-server.service \-f  |
| :---- |

Pour le **Rockchip RK3588** (4× Cortex-A76 \+ 4× Cortex-A55, ARMv8.2-A, GPU Mali-G610 MP4), les ajustements critiques par rapport au CIX CD8180 consistent à retirer les instructions ARMv9 (`sve2`, `i8mm`, `bf16` — qui provoqueraient un `SIGILL` sur Cortex-A76), cibler `armv8.2-a+dotprod+fp16+crypto` avec `-mtune=cortex-a76`, et aligner l'affinité `systemd` sur les **4 cœurs Cortex-A76 (`CPU 4-7`)**. 

| Paramètre | CIX CD8180 (Orange Pi 6 Plus) | Rockchip RK3588 (Orange Pi 5\) |
| :---- | :---- | :---- |
| **ISA (**GGML\_CPU\_ARM\_ARCH**)** | armv9.2-a+i8mm+sve2+bf16+dotprod+fp16+crypto | armv8.2-a+dotprod+fp16+crypto |
| **Tuning GCC** | Générique ARMv9.2-A | \-mtune=cortex-a76 |
| **KleidiAI** | Micro-noyaux i8mm / SVE2 | Micro-noyaux dotprod (SDOT) |
| **Affinité CPU (**systemd**)** | 4 5 6 7 8 9 10 11 (8× A720) | 4 5 6 7 (4× A76) |
| **Threads par défaut** | 8 | 4 |
| **GPU Vulkan** | Immortalis-G720 MC10 | Mali-G610 MP4 (PanVK sur Kernel 7 / Mesa) |

**Note sur PanVK / Mali-G610 :** Si le Mali-G610 n'apparaît pas ou si une quantification précise (ex. Q4\_K\_M) provoque un ralentissement sur PanVK, passez simplement LLAMA\_NGL=0 dans /etc/default/llama-server pour basculer sur l'exécution CPU pure (Cortex-A76 \+ dotprod \+ fp16), ou testez Q4\_0 qui exploite directement les micro-noyaux KleidiAI SDOT.

Adapter `ai-memory-booster` pour remplacer **Ollama** par **`llama-server`** consiste à traduire quatre appels HTTP (chat, génération, embeddings et métadonnées du modèle) vers l'API compatible OpenAI (`/v1/...`).

Il existe toutefois un **point d'architecture critique** à anticiper avant de toucher au code : contrairement à Ollama qui charge à la volée un modèle de chat et un modèle d'embeddings sur le même port, une instance de `llama-server` ne charge qu'**un seul modèle GGUF à la fois**. Comme `ai-memory-booster` attend par défaut des vecteurs de dimension **768** (`"dimension": 768` dans `config.json`) pour ChromaDB, la solution la plus propre sur RK3588 (32 Go) et CIX CD8180 est de faire tourner :

* **`llama-server` (port `8080`)** pour le chat et les résumés (`llama3.2`, `mistral`, `gemma`, etc.).  
* **`llama-server` (port `8081`)** en mode `--embedding` avec un modèle dédié léger comme `nomic-embed-text-v1.5-Q8_0.gguf` (\~145 Mo en RAM, 768 dimensions exactes).

## **1\. Correspondance des endpoints (Ollama → `llama-server`)**

| Méthode ai-memory-booster | Endpoint Ollama (:11434) | Équivalent llama-server (:8080 / :8081) |
| :---- | :---- | :---- |
| chat() | POST /api/chat | POST :8080/v1/chat/completions |
| generate() | POST /api/generate | POST :8080/v1/completions (ou /v1/chat/completions) |
| Embeddings (ChromaDB) | POST /api/embed ou /api/embeddings | POST :8081/v1/embeddings |
| getLlmSpec() | POST /api/show | GET :8080/props et GET :8080/v1/models |

### **Intégration dans `core/`**

Dans le module de `core/` qui instancie actuellement le client Ollama (`ollama` npm package ou appels `axios`/`fetch` vers `:11434`) :

1. **Remplacez** l'import Ollama par `const LlamaServerClient = require('./llamaServerClient');`.  
2. **Instanciez** `const llm = new LlamaServerClient(config);`.  
3. **Substituez** les appels :  
   * `ollama.chat(...)` → `await llm.chat(messages)`  
   * `ollama.generate(...)` → `await llm.generate(prompt, config.rolePrompt)`  
   * `ollama.embeddings(...)` / `ollama.embed(...)` → `await llm.embed(text)`  
   * `ollama.show(...)` → `await llm.getLlmSpec()`  
4. **Désactivez** les champs `keep_alive` spécifiques à Ollama : avec `llama-server`, le modèle reste résident en permanence en RAM/VRAM tant que le service `systemd` tourne (pas besoin de `baseKeepAlive` / `extendedKeepAlive`).

## **5\. Alternative sans modifier `ai-memory-booster`**

Si vous voulez conserver le dépôt `aotol/ai-memory-booster` intact (pour suivre les mises à jour upstream sans conflit Git), vous pouvez placer un **micro-proxy Node.js sur `127.0.0.1:11434`** qui intercepte `/api/chat`, `/api/generate`, `/api/embed` et `/api/show` et les redirige vers `:8080` et `:8081`. Pour `ai-memory-booster`, `llama-server` devient alors totalement transparent.
